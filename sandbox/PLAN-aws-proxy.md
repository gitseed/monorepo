# AWS Read-Only Proxy Integration Plan

## Problem

Wire AWS read-only API access into the credentials proxy alongside the existing
bearer-token upstreams (OpenRouter, GitHub, Cloudflare, etc.). AWS uses SigV4
request signing, not bearer tokens, so the existing `credential_injector` pattern
doesn't apply.

## Decision: Envoy `aws_request_signing` filter

The proxy (Envoy) signs outgoing requests with SigV4 using the
`envoy.filters.http.aws_request_signing` filter. The agent makes unsigned HTTP
calls to the proxy; the proxy signs and forwards to AWS.

This filter is available in the `envoyproxy/envoy:v1.39-latest` image already in
use (`sandbox/container/proxy.containerfile`). It is a contrib filter but is
included in the standard Docker image.

## Inputs

Two data sources, both already on disk:

1. **`sigv4/signing_names.json`** — 429 services mapped to their SigV4 signing
   name. 428 use SigV4; 1 (`codecatalyst`) is `null` (bearer auth). Generated by
   the Tofu project in `sigv4/tofu/` which crawls all ~430 Smithy models from
   `aws/api-models-aws` and extracts the `aws.auth#sigv4` trait.
2. **Regions** — 34 standard-partition AWS regions. Trivially enumerable; can
   be hardcoded or fetched from SSM public parameters
   (`/aws/service/global-infrastructure/regions`).

## The math (REVISED)

| Component | Entries |
|---|---|
| SNI filter chains (wildcard patterns) | 69 |
| Per-service-per-region routes (428 × 34 regions + global) | ~15,000 |
| TLS cert wildcard SANs | 69 |

The original estimate of 497 entries was wrong. The 69 SNI wildcards reduce
**filter chains** from ~15,000 to 69, but routes within each filter chain must
still be per-service-per-region because the `AwsRequestSigningPerRoute` override
replaces the entire filter config (both `service_name` and `region`), not
individual fields. The 69 SNI wildcards collapse the **filter chain** dimension;
the per-service-per-region **route** dimension remains.

This is still generated programmatically from `signing_names.json` + 34 regions
and is manageable — Envoy handles large configs without issue. The 69 wildcard
SANs (instead of ~15,000 enumerated SANs) is the real win for cert generation.

## Validated findings (2026-08-09)

All six open questions resolved:

### Q1: SigV4A wildcard regions — DOES NOT WORK universally ✗

**Question:** Can `signing_algorithm: AWS_SIGV4A` with `region: '*'` avoid
per-region signing config?

**Answer:** No. SigV4A with `region: '*'` is supported by the Envoy filter
(confirmed in the
[AwsRequestSigning proto docs](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/filters/http/aws_request_signing/v3/aws_request_signing.proto)),
but it only works for multi-region/global AWS services. AWS regional services
(EC2, Lambda, etc.) require SigV4 with a specific region. SigV4A is asymmetric
signing (ECC keys) designed for services like S3 Multi-Region Access Points and
CloudFront. Regional endpoints reject SigV4A signatures.

**Impact:** The region dimension cannot be collapsed. We need per-service-per-region
signing config (~15,000 entries generated from `signing_names.json` × 34 regions).

### Q2: Egress wildcard matching in Envoy — CONFIRMED ✓

**Question:** Does Envoy's `filter_chain_match.server_names` support
`*.us-east-2.amazonaws.com` wildcard patterns?

**Answer:** Yes. The Envoy docs
([listener_components.proto](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/listener/v3/listener_components.proto))
explicitly state:

> The server name will be matched against all wildcard domains, i.e.
> `www.example.com` will be first matched against `www.example.com`, then
> `*.example.com`, then `*.com`.

Caveats: partial wildcards (`*w.example.com`) are invalid. Bare `*` is not
supported (omit `server_names` instead). `*.us-east-2.amazonaws.com` is valid
and matches `ec2.us-east-2.amazonaws.com` (one label between `*` and the suffix).

### Q3: TLS cert SAN strategy — Wildcard SANs ✓

**Question:** Wildcard SANs vs. enumerated SANs?

**Answer:** Use 69 wildcard SANs — one per SNI wildcard pattern:
- `*.amazonaws.com` (global services)
- `*.{region}.amazonaws.com` × 34 (regional services)
- `*.{region}.api.aws` × 34 (dualstack regional services)

A single cert with 69 wildcard SANs covers all AWS endpoints. Wildcard SANs
cover exactly one label, so `*.amazonaws.com` matches `sts.amazonaws.com` but
NOT `ec2.us-east-2.amazonaws.com` (two labels). This is why per-region wildcards
are needed. The tofu cert generator needs to emit these 69 wildcard SAN entries
instead of ~15,000 enumerated SANs.

### Q4: Read-only IAM policy — `ReadOnlyAccess` managed policy

Use the AWS-managed `ReadOnlyAccess` policy. It grants read access to all
services. If finer-grained control is needed later, add service-specific
read-only inline policies. Defined in the ouroboros Tofu config.

### Q5: Credential refresh — Static env vars (no refresh needed)

Use static IAM access keys (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`) as
environment variables. No refresh needed. If STS short-lived credentials are
needed later, the `aws_request_signing` filter caches credentials for 1 hour and
refreshes automatically — no additional proxy config required. The filter uses
the standard AWS credential chain, so switching to STS is a matter of changing
the env vars, not the Envoy config.

### Q6: `upstreams.yml` vs. generated config — Generate from `signing_names.json` ✓

**Decision:** Option B — extend `envoy.pkl` to read `signing_names.json` directly
(Pkl can import JSON) and generate AWS filter chains + clusters alongside the
existing `credential_injector` chains. This keeps a single source of truth in Pkl
with no extra build step. `upstreams.yml` stays small (6 bearer-token entries);
AWS config is generated from the 429-service `signing_names.json` + 34-region
list at Pkl eval time.

## Open questions

All resolved. See "Validated findings" above.

## Revised architecture

### Config generation

`envoy.pkl` reads `signing_names.json` (429 services) and a 34-region list, then
generates:

1. **69 SNI filter chains** — one per wildcard pattern (1 global + 34 regional
   `.amazonaws.com` + 34 regional `.api.aws`). Each filter chain has its own HCM
   with routes for all 428 SigV4 services.
2. **~15,000 routes** — one per service per region. Each route has:
   - Domain match for `{service}.{region}.amazonaws.com` (or `.api.aws`)
   - `AwsRequestSigningPerRoute` override with `service_name` (from
     `signing_names.json`) and `region` (from the filter chain's SNI pattern)
   - Cluster pointing to `{service}.{region}.amazonaws.com:443`
3. **69 wildcard SANs** in the TLS cert — one per SNI wildcard pattern.

### `AwsRequestSigningPerRoute` caveat

The `AwsRequestSigningPerRoute` proto overrides the **entire** `AwsRequestSigning`
message, not individual fields. Each per-route override must specify both
`service_name` and `region`. The global filter default is overridden completely
per route. This is why the config size is per-service-per-region, not per-service.
